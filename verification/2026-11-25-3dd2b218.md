## 2. T2 — the latent gate defect, reproduced and fixed

### 2.1 Symptom (measured on `main` @ `4c0ff8d`)

`npm test` failed at its last suite:

```
FAIL negative control: a null settlement_ts still renders a blank, never an inferred time
settlement-ts: 4 passed, 1 failed
```

**Why this was still latent on `main`.** `main` had advanced only by `GITHUB_TOKEN` data pushes since 2026-11-22.
GitHub does not run push workflows for token pushes (see the repository's own F-80/F-83 findings and
[GitHub: triggering a workflow from a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow-from-a-workflow)).
Confirmed from the Actions API: the only workflow runs on `main` between 2026-11-22 and this session were
`pages build and deployment`, `keepalive`, `live-alerts` and `Refresh demo data snapshot` — **no `site-qa`, `suite-qa`
or `alerts-qa` run**, so the broken gate had never been exercised against the refreshed capture.

### 2.2 Cause (traced, not guessed)

`scripts/check-settlement-ts.mjs` hard-coded a real settlement instant, `2026-11-16T14:32:51.060078Z`, patched it
into `topics.gas.settled_events[0]`, and then asserted the whole generated gas page no longer contained that
instant after the negative control removed it from that one event.

Measured on the committed capture of `2026-11-25T12:12:22.961Z`:

| Settled event (gas topic, in capture order) | Own `settlement_ts` |
|---|---|
| `settled_events[0]` = `KXAAAGASW-26NOV23` | `2026-11-23T15:06:33.579832Z` |
| `settled_events[1]` = `KXAAAGASW-26NOV16` | `2026-11-16T14:32:51.060078Z` ← the hard-coded instant |

The control therefore blanked the **wrong** event; the second event still rendered the instant and the assertion
failed although the generator was correct. On 2026-11-22 the capture happened to list `KXAAAGASW-26NOV16` first, so the
same fixture passed. This is the same class of order-dependent flakiness recorded as **F-89**, whose fix nulled
every market *inside event 0* and therefore still depended on which event came first.

> **Concurrent independent fix (noted for accuracy).** While this integration was in progress, **session-13a3df7d**
> measured the same order dependence from a different angle — *"the control nulled only `settled_events[0]` while
> `categories/gas.html` renders 12 settled events, so the other 11 rows still rendered their timestamps"* — and
> merged a fix as [PR #113](https://github.com/kanlerxz87-cyber/KalshiDash1/pull/113) (`343ecc9`, 12:27:59Z), with
> its record merged as [PR #115](https://github.com/kanlerxz87-cyber/KalshiDash1/pull/115) (`2dcb377`). The two
> sessions worked from the same base `4c0ff8d` and neither had seen the other's work.
> **Resolution:** the merged tree keeps the stronger implementation, which **subsumes** session-13a3df7d's fix — it
> nulls `settlement_ts` on every settled event **of every topic** (theirs covered the gas topic only) and adds the
> two properties their version did not have (the order-independent sentinel, and the cell-level assertion that can
> detect an inferred time). Their measurement is cited in the code comment, their board section is preserved
> verbatim, their commits remain in `main`'s history, and the **F-93 row credits them explicitly**. Nothing of
> theirs was reverted, renumbered or rewritten. **Their fix alone would not have caught §2.3.**

### 2.3 A second, independent weakness found by mutation testing

The assertion only looked for **one string**. Mutating the generator so it fell back to a constant time
(`r.ev.settlement_ts || r.m.settlement_ts || '2026-01-01T00:00:00Z'`) still produced a **passing** gate, because the
inferred value was a different string. The control could not, in principle, detect a generator that inferred a time.

### 2.4 The fix

Test-only. The generator, the capture script and every published page are untouched.

1. **The positive control now uses a sentinel instant that occurs nowhere in the snapshot**
   (`2031-01-02T03:04:05.678901Z`), and a new assertion proves the sentinel is absent from the committed capture, so
   the positive control can never be satisfied by a real row the fixture never touched.
2. **The negative control now removes `settlement_ts` from every settled event of every topic** — the event field
   *and* every nested market's field — which is the only way to assert "no official value anywhere ⇒ no time rendered
   anywhere".
3. **The negative control now reads the rendered "Settled at" cell** (the 6th cell of each resolved-events row) and
   fails if *any* of them contains a date, instead of searching the page for one hard-coded string.

### 2.5 Verification

| Check | Result |
|---|---|
| `npm run test:settlement` on the current capture | **6/6 pass** (was 4 passed / 1 failed) |
| Reverting only the fixture to the pre-fix version on the same data | reproduces the original failure |
| **Mutation:** generator made to fall back to a constant time | control now **fails on 100 rows** and exits 1 (`the generator rendered an inferred settlement time in 100 row(s): <td>2026-01-01 00:00:00 UTC</td>`) — i.e. the control is a real guard, not a tautology |
| Published pages / captured data changed by the fix | **none** — `git diff` touches only the test script |

Published as **F-93** on the Flagged for Review page with the mutation evidence.

## 5. Limits — what is deliberately blank, and why

These are **not** defects and are **not** silently filled in:

1. **The demo account is disconnected.** `data/account.json` says `connected: false`, `captured_at: null`. No
   `KALSHI_KEY_ID` / `KALSHI_PRIVATE_KEY` secret exists in this repository, none was requested, and no authenticated
   read or order was made. Consequently **no balance, position, fill, settlement or realized return is claimed
   anywhere**, and the account page shows the disconnected state with its privacy warning (F-85).
2. **No resolution has been recorded yet.** The feed's `resolutions` array is empty because the tracked markets have
   not published a `result` of yes or no. The pages say so instead of showing an example.
3. **No cause is attributed to any price move.** The catalyst page links official settlement sources and clearly
   labelled discovery links; causation is not established by the API and is not asserted.
4. **Dollar figures are derived estimates.** `est_traded_dollars` = contracts × the contract's published notional
   value; it is not an official dollar-volume field and not an exchange-wide census (F-03).
5. **The ROI score is a published heuristic**, not a measured or back-tested return. Its terms and weights are shown
   on every row so a reader can audit it.
6. **The sampling cadence is what the platform delivers**, not what the cron declares (F-83). GitHub documents that
   scheduled runs may be delayed or dropped.
7. **The high-ROI pane is currently dominated by non-oscillating rows.** Of the 14 `highROI: true` rows, the
   oscillation rows are excluded by the follow-through gate; the rest are `KXPRESNOMD-*` and `KXBTCY-*` rows whose
   published quote does sit at the swing price. The gate's behaviour is documented in the engine's header comment and
   in each row's "model terms".
8. **Browser CORS limits remain.** The page fetcher in this sandbox could not read the demo API cross-origin, so the
   live pages fall back to the committed engine feed and say so plainly ("Showing the engine feed.").
