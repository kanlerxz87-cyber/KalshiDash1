## 3. Remaining, separate defect found and fixed here (W-06)

The repository's own health monitor hid the outage.

`scripts/keepalive.mjs` judged a workflow by the **age of its newest run** and ignored the run's
**conclusion**. Measured output at 06:38Z on 2026-11-21, before the fix:

```
· live-alerts.yml
    newest run:      2026-11-21T06:27:20Z → 1 min ago
    newest SCHEDULED: 2026-11-21T02:54:41Z → 3.6 h ago
    verdict:         fresh (1 min ago)
```

Every scheduled run of that workflow had failed, and the "1 min ago" run was an unrelated `push`.
The monitor printed **`fresh`** immediately above its own evidence that the sampler had not
succeeded in 3.6 hours. This matters because the site's "never claim to be live on its own"
guarantee is checked by this monitor.

**Fix.** New `scripts/keepalive-verdict.mjs`:
- `fresh` requires a **successful** concluded run inside the window;
- a newest run that did not succeed is reported `FAILING`, whatever its age;
- `queued` / `in_progress` runs are never treated as evidence;
- scheduled-stale is detected separately, so a recent successful *push* run cannot mask a dead cron:
  `fresh (2 min ago) · scheduled run 3.7 h ago (failure)`;
- an unparseable timestamp yields `null` age, never `0`;
- `--strict` fails the pulse; `--exclude-self` stops a workflow gating on its own in-flight run.

**Tests.** `scripts/check-keepalive-verdict.mjs` — 27 offline assertions built from the **real** run
histories measured above, including the exact case that was misreported. Output:
`keepalive verdict checks: 27 passed, 0 failed`.

The monitor is wired into `keepalive.yml` as a **non-fatal** step. The hard failure stays with
`tools/freshness_check.mjs`, so there is exactly one gate. Reason: GitHub documents that
`scheduled` runs are delayed and can be dropped
(<https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule>),
and that limitation is already flagged as F-58. Making a *dropped cron* red would not have helped —
the failure this session fixed was a **broken script**, which `--strict` does now surface.

## 4. Second latent bug, reproduced but NOT fixed (handed to the next session)

Independent of the `fi` syntax error, the write-back loops are still fragile. Reproduced against a
scratch bare remote:

1. writer A regenerates `data/snapshot.json` and commits;
2. writer B publishes a different `data/snapshot.json`;
3. writer A runs its verbatim loop (`git fetch` → `git rebase FETCH_HEAD` → `git push`):

```
Auto-merging data/snapshot.json
CONFLICT (content): Merge conflict in data/snapshot.json
rebase exit=1
```

The `for` loop then retries the **identical** conflicting rebase, because nothing about it changes
between attempts. Second failure mode: when the rebase is a silent no-op the loop pushes a ref that
is already an ancestor and reports success without publishing.

Related: `keepalive.yml` states "*the other two writers queue behind this one (see the shared group
name in live-alerts.yml and refresh-data.yml)*", but they do not share a group —
`keepalive.yml` uses `writer-${{ github.ref }}`, `live-alerts.yml` uses `live-alerts`, and
`refresh-data.yml` uses `refresh-data-${{ github.ref }}` (`grep -n 'group:' .github/workflows/*.yml`).
So the three writers never serialise.

The simplest correct fix is to regenerate-and-retry instead of rebasing a committed data file
(discard the local commit, re-run the generator, commit again), and to put all three writers in the
same concurrency group. **Not changed here** — those files belong to `session-4251f2d1`'s scope, and
changing them now would collide with that repair. Logged as a request in `COORDINATION.md`.
