## 3. Defect found and fixed: **F-80** (engine samples left the site stale)

`main` was **not internally consistent**: `node scripts/build-site.mjs --check` failed from a clean checkout, listing
all 22 generated pages. Measured commit by commit:

| Commit on `main` | `--check` | feed `generated_at` | `index.html` `data-asof` |
|---|---|---|---|
| `017bd63` | FRESH | 17:42:16Z | 17:42:16Z |
| `82d70f8` (engine sample) | **STALE** | 23:12:17Z | 17:42:16Z |
| `c39c52f` (snapshot refresh) | **STALE** | 23:12:17Z | 17:42:16Z |
| `14bfb12` (engine sample) | **STALE** | 23:13:08Z | 17:42:16Z |

**Cause.** `live-alerts.yml` staged only `data/live/`; the pages embed `feed.meta.generated_at`, so each sample changed
what the pages should say and left them saying the old thing. `refresh-data.yml` and `keepalive.yml` stage
`'*.html' assets categories` too — the engine was the only writer with the gap.

**Why CI did not stop it.** Those commits were pushed with the default `GITHUB_TOKEN`, and
[GitHub documents](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)
that such pushes "will not create a new workflow run" — so `Site build check` never ran on them. Its last run
(`44960595512`) was on `017bd63`, which was still fresh.

**Overlap, handled without discarding anyone's work.** Three sessions reached this in parallel:
`session-2ea8e33c` fixed the *gate* side (F-76: `--check` no longer counts the as-of clock alone as stale),
`session-e50b53f6` fixed the *writer* side (F-78, republished as F-80 on `main`), and this session independently
measured and fixed the writer side. Both of this session's earlier IDs collided with rows that landed first, so the row
was renumbered to **F-80** and its text now credits the earlier fix and records only what is new — no other session's
row, script, workflow or data was removed.

### What this session actually adds beyond the merged fix

The merged fix made the rebuild **best-effort**:

```yaml
node scripts/build-site.mjs >/dev/null 2>&1 || \
  echo "::warning::site rebuild failed; committing the sample without regenerated pages"
```

A failing rebuild therefore still committed the sample, and the run stayed green — the same defect, now silent. Three
changes close that, none of which change what is published when the generator works:

1. the rebuild runs **before anything is staged** and is **mandatory** — `if ! node scripts/build-site.mjs; then exit 1; fi`;
2. the conflict-regenerate path rebuilds and retries rather than proceeding;
3. after the verified push the step runs `node scripts/build-site.mjs --check` against the **tree that landed**.

**New offline guard:** `scripts/check-workflow-site-consistency.mjs`, 20 assertions, wired into `npm test`
(`test:writers`) and `site-qa`. For all three writers it asserts that a committed sample is committed *with* the pages
generated from it, that the rebuild precedes staging, and that the rebuild is **mandatory**. Its negative controls
include the exact `|| true` shape above, so returning to best-effort fails the suite. This is needed precisely because
the CI gate cannot be relied on for token-pushed commits.
