## 1. Why the question had stayed open

`F-01` was published on 2026-11-20 as *"Browser access (CORS) to the demo API could not be tested from the build
sandbox. The live tables depend on it."* That was accurate: the sandbox used for every offline check in this
repository has **no egress** to `external-api.demo.kalshi.co`:

```
$ curl -sS -i -H 'Origin: https://kanlerxz87-cyber.github.io' \
    https://external-api.demo.kalshi.co/trade-api/v2/exchange/status
curl: (35) OpenSSL SSL_connect: SSL_ERROR_SYSCALL in connection to external-api.demo.kalshi.co:443
```

`session-549a3b66` recorded the same limitation as `ECONNRESET` (see `verification/2026-11-21-549a3b66.md`).
Repeating the attempt from the sandbox would therefore have produced another "untested" row, which is why several
sessions left it open rather than guessing.

**What changed here:** CORS is decided by *response headers*, and a GitHub Actions runner **does** have egress to the
demo host — `tools/live_engine.mjs` samples it successfully several times a day. So the measurement was taken on a
runner, with the same `Origin` the published site uses, and the raw headers were committed as evidence.

Every public endpoint answered with the requesting origin echoed, on both runs:

| Endpoint | HTTP | `access-control-allow-origin` |
|---|---:|---|
| `GET /exchange/status` | 200 | `https://kanlerxz87-cyber.github.io` |
| `GET /markets?limit=1` | 200 | `https://kanlerxz87-cyber.github.io` |
| `GET /series?category=Culture&include_volume=true` | 200 | `https://kanlerxz87-cyber.github.io` |
| `GET /markets/KXPRESNOMD-28-AKLO/orderbook?depth=5` | 200 | `https://kanlerxz87-cyber.github.io` |
| `GET /markets/trades?ticker=KXPRESNOMD-28-AKLO&limit=5` | 200 | `https://kanlerxz87-cyber.github.io` |
| `GET /series/KXPRESNOMD/markets/KXPRESNOMD-28-AKLO/candlesticks?period_interval=1` | 200 | `https://kanlerxz87-cyber.github.io` |
| `GET /portfolio/balance` (no key on purpose) | 401 | `https://kanlerxz87-cyber.github.io` |

Also recorded on every response: `access-control-allow-credentials: true` and
`access-control-expose-headers: X-Csrf-Token,X-Ratelimit-Limit,X-Ratelimit-Remaining,X-Ratelimit-Reset,X-Ratelimit-Cost`.

Two things worth stating precisely, because they are easy to over-claim:

* The header is **not** a wildcard: it echoes the requesting origin. A second request with
  `Origin: http://localhost:8000` came back with `access-control-allow-origin: http://localhost:8000`
  (`echo_test.acao_changes_with_origin: true`). So the demo host reflects arbitrary origins; that is a property of the
  exchange, recorded here, not endorsed, and it does not change what this site does.
* CORS policy is **not** a guarantee about an individual visitor's network. A proxy, DNS filter or extension can still
  block the host. The pages detect that at run time and fall back to the committed snapshot, and the freshness badge
  reports the age of the last engine sample independently.

A transient failure in run 1 (`/series?category=Culture` → `fetch failed` after 4.7 s, while its neighbours answered in
~300 ms) was **not** turned into a finding: the probe was changed to retry (3 attempts, 15 s bound), and run 2 answered
every request on the first attempt (`attempts: 1`). No conclusion was drawn from the single timeout.

### 2.2 Signed requests — blocked (new flag F-66)

A browser must send a preflight before any request that carries custom headers. Both preflights were answered `204`:

```
access-control-allow-methods: GET,POST,PUT,PATCH,DELETE,HEAD,OPTIONS
access-control-allow-headers: Origin,Content-Length,Content-Type,Idempotency-Key,X-Csrf-Token,X-Aws-Waf-Token,
                              Traceparent,Tracestate,... (29 names; see data/cors-probe.json)
```

`KALSHI-ACCESS-KEY`, `KALSHI-ACCESS-SIGNATURE` and `KALSHI-ACCESS-TIMESTAMP` — the three headers Kalshi requires on
every authenticated request — are **not** in that list (checked programmatically:
`allows_requested_headers: false` for both the signed GET and the order POST). The browser therefore fails the
preflight and never sends the request, regardless of client code.

Consequence, and it is the reason this is published as a flag rather than a footnote: **a static page cannot read a
portfolio or place an order against Kalshi.** Execution in this repository already happens in GitHub Actions
(`tools/demo_trader.mjs`, repository secrets), and the browser only reads `data/account.json`. The copy that implied
otherwise was wrong and is corrected in this commit (§3).

Sources for the required headers and the CORS rules:

* [Quick Start: Authenticated Requests](https://docs.kalshi.com/getting_started/quick_start_authenticated_requests.md)
  — the three `KALSHI-ACCESS-*` headers, millisecond timestamps, and the `timestamp + METHOD + path` signature.
* [WHATWG Fetch — CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol) — `Access-Control-Allow-Origin`
  and the `Access-Control-Allow-Headers` requirement for preflighted requests.
* [Kalshi: demo environment](https://docs.kalshi.com/getting_started/demo_env) — the demo host used above.
* [Get Exchange Status](https://docs.kalshi.com/api-reference/exchange/get-exchange-status.md) — the endpoint whose
  200 response was read in both runs.
