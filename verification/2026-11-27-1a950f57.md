## 1. Method and how to re-run it

The Arena sandbox's egress allowlist covers only `github.com`, `codeload.github.com`, `api.github.com`,
`registry.npmjs.org`, `pypi.org` and `files.pythonhosted.org`, so `curl https://docs.kalshi.com/...`
fails here. Official pages were read through the page-fetch tooling, and the automated check runs on a
GitHub runner, which has general HTTPS egress.

| Gate | Command | Evidence |
|---|---|---|
| Citation existence (offline parser tests) | `npm run test:external-sources-selftest` | 20 checks, positive and negative controls, no network |
| Citation existence (produce evidence) | `npm run verify:external` | writes `data/external-source-check.json` |
| Citation coverage (blocks a PR) | `npm run test:external-sources` | fails if any current citation is not covered by the evidence |
| Workflow shell syntax | `node scripts/check-data-workflow-shells.mjs` | 24 block scripts across 11 workflows |
| Row-source rule | `npm run test:rows` | 20 canonical pages, approved-publisher links |
| Full battery | `npm test` | 24 suites, all green on this branch |

The external check asks Kalshi only for its **own listings** — `llms.txt` (the documentation index) and
`sitemap.xml` — and compares canonical page URLs. It never reads page content and never rewrites a URL to a
plausible-looking one.

## 3. Defect found, verified and fixed — `F-SOURCE-02`

The new check's first run reported one cited documentation page the publisher does not list:
`https://docs.kalshi.com/api-reference/search/get-tags-by-categories`, linked from the
`GET /search/tags_by_categories` row on `api.html`.

* **Not listed** by either publisher index: absent from [llms.txt](https://docs.kalshi.com/llms.txt) and
  from [sitemap.xml](https://docs.kalshi.com/sitemap.xml).
* **Does not serve a page:** fetching it returns a fetch error, not a document.
* **The endpoint is documented under another slug:**
  [Get Tags for Series Categories](https://docs.kalshi.com/api-reference/search/get-tags-for-series-categories)
  returns HTTP 200 and documents exactly `GET /search/tags_by_categories` with the same `tags_by_categories`
  response object the site reads.

Fixed in `templates/api.tpl` to the publisher's listed page, regenerated through `scripts/build-site.mjs`,
and published as `F-SOURCE-02` on [flagged.html](../flagged.html#F-SOURCE-02). The replacement path is the
one Kalshi lists — not an inferred similar URL.

**Why this matters for a trader:** the broken row was the one that explains how the Golf topic is chosen
(the official `Golf` tag), so the claim could not be checked from the site at all. A "source link" that is a
dead end is worse than a missing one, because it looks verified.

## 4. Own defects found and corrected during review

| Citation extractor | Matched documentation URLs anywhere in the text, so the Flagged row that *quotes* the dead path in order to explain it was itself reported as a broken citation. | Citations are `href` targets plus `url` fields in `data/sources.json`; a quoted path is not a citation. | Workflow shell gate | Hard-coded three files while the repository had ten workflows, so `demo-account.yml` — the only workflow handling the Kalshi credentials — was never shell-checked. | Discovers every workflow (24 block scripts across 11), asserts the discovery, and keeps positive/negative controls. |
| Requirements table sources | The new page was not in the row-source gate's `REQUIRED` list, so 14 of 20 rows carried only internal links. | Page added to the gate; every row links the Kalshi doc for an exchange rule or the repository code/README for a project decision. 20 rows, 100 % approved source. |

## 5. Limits of this record (stated, not hidden)

* **Existence, not content.** The automated check proves a cited page is listed and reachable. It does not
  prove the page still says what the site quotes; that remains the job of the dated records.
* **One sample.** Market values quoted in §2 are one live read on 2026-11-27, not a time series.
* **Scope of the external check.** Only `docs.kalshi.com`. Other external publishers (GitHub, AAA, the
  HTML/Fetch spec pages) are not probed by it.
* **Not re-verified here:** the 1,032 static table rows' semantic accuracy (covered by
  `verification/2026-11-27-a1ded21f.md` and `2026-11-27-155a1ceb.md`), the demo-account connection state
  (`connected: false`, unchanged), and the alert-feed cadence (`F-83`, unchanged — GitHub delivers the
  scheduled runs far less often than the declared cron).
* **Concurrent work.** `main` advanced through PRs #139–#144 while this branch was open. The merge kept
  the other sessions' `package.json` test chain (`console-chart`) alongside this session's
  (`external-sources`); nothing was reverted.

## 6. Deploy failure found after merge, and the guard it produced — `F-CHART-03`

PR #149 merged with every check green. Two GitHub Pages builds then reported `status: errored`
(`4f11cbb`, the merge commit, and `66e9af0`, the bot commit right after it). This is the one thing that must not be
left standing, so it was reproduced before anything was changed.

**Reproduced at both commits, in a clean worktree:**

```
$ git checkout 4f11cbb && node scripts/build-site.mjs --check
Committed site is stale for: requirements.html
```

`requirements.html` quoted the previous data sample in its generated footer
(`Snapshot captured 2026-11-27 22:39:18 UTC`) while the same tree's `data/snapshot.json` carried `22:43:05`. A
data writer published data and HTML without regenerating that page.

**Why it was invisible to the existing gates:** the `--check` exception for the alert sample clock is matched by
*content*, so a page embedding an older value is indistinguishable from a page the exception does not cover; the
footer's `Snapshot captured … UTC` clock was not normalised at all; and the staleness self-test rebuilt its scratch
tree before inspecting it, which erases the defect being looked for.

**Fixed in two places** (`PR #154`, merged as `c500684`):

1. `scripts/build-site.mjs` normalises the footer clock next to the alert stamp, so `--check` reports the real change.
2. `scripts/check_build_staleness.mjs` reads the **committed** pages and fails if any of them quotes a clock that is not
   this tree's data (scoped to the generated `<footer>`, so the Flagged page may still *quote* a stale clock as evidence).
   **Negative control run:** rewinding one page's footer made the guard fail and name the page; restoring it passes
   (12 assertions).

**Verified live:** `https://kanlerxz87-cyber.github.io/KalshiDash1/requirements.html` and `.../flagged.html` serve the
merged content, and `main` @ `c5573bd` passes `build-site.mjs --check`, `check_build_staleness.mjs` and the full
`npm test` battery.

**Recorded inconsistency, not resolved:** the Pages build record for `c500684` reads `status: errored, duration 0`, while
the `Site build check` run for the same SHA succeeded, the exact step body passes on that tree in a clean worktree, and
the builds immediately before and after are `built` with the content live. Both readings are published on the board
rather than one being asserted.
