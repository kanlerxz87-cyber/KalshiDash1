## 4 · Findings

### F-82 — the dashboard chats never read the committed engine feed (fixed)

**Measured before the fix.** On a browser that cannot reach the demo API, `pages.dashboard` fell back
to `seedAlertsFromSnapshot`, which reconstructs moves from captured 1-minute candles; the engine feed
(`data/live/feed.json`) was read only by the alerts console. The published page therefore displayed a
synthetic replay and an empty high-ROI pane while 40 real alerts existed in the repository.

**Fix (`assets/app.js`).** New `engineAlertRows()` + `loadEngineFeed()`:

- rows are copied from the feed; a row is **dropped** (never repaired) when its time is unparsable, a
  price is missing, a price is outside $0–$1, or `|delta|` is below the feed's own threshold;
- the engine's 0–1 score is printed as `engine score 0.78 / 1` and is **not** rescaled into the
  browser's 0–100 research score (two different formulas — F-OBS-01);
- the high-ROI pane selects engine rows by the engine's published `model.highROI` (and
  `tradeable !== false`), not by the browser's ROI cut;
- engine rows print `MM-DD HH:MM:SS UTC`, so a hours-old sample can never read as "today";
- the badge `title` names the exact sample the row came from, and the snapshot-mode notice says the
  chats are the engine's committed alerts;
- when real engine alerts exist, the synthetic replay is removed from the stored log;
- the right pane's message plural (which used the left pane's length) is corrected.

**Regression test.** `scripts/check-market-chart.mjs` gained a dashboard-with-feed scenario
(7 assertions; suite 31 → **38** cases): both panes populated, verbatim prices and exact API URLs,
four dropped-row shapes, the `/ 1` scale, the dated timestamp, and replay removal. **Negative
control:** the same test against the pre-fix `app.js` fails with
`TypeError: Cannot read properties of undefined (reading 'length')`.

### F-83 — "runs every 10 minutes" was published; the platform delivers ≈1 run per 5.8 h (flagged)

Declared crons vs the repository's own runs: `live-alerts` `*/10` → 6 runs/34.6 h; `keepalive` → 4
scheduled runs in the same window; `demo-account` `17 */6 * * *` → 4 runs (23:58, 07:03, 19:12,
06:43). GitHub documents the delay/drop behaviour; nothing in this repository can raise the rate.
Copy corrected in `README.md`, `docs/ALERTS.md` and `EXECUTIVE_SUMMARY.md` to state declared cron +
measured delivery and link the finding. **Not resolved and not resolvable here** — published for
review. The measured sample age is already shown on every page (`assets/freshness.js`, `STALE` past
45 minutes), so the site does not claim to be live when it is not.
