## Official contracts checked

- **Environment:** [Kalshi's demo documentation](https://docs.kalshi.com/getting_started/demo_env) lists `https://external-api.demo.kalshi.co/trade-api/v2` and `https://demo-api.kalshi.co/trade-api/v2` as the recommended and alternate demo REST roots. Demo funds are mock funds; demo prices and behavior may not reflect real markets. The CLI's allowlist is an additional project safety policy, not an exchange guarantee.
- **Authentication:** [Quick Start: Authenticated Requests](https://docs.kalshi.com/getting_started/quick_start_authenticated_requests) specifies the three `KALSHI-ACCESS-*` headers, a millisecond timestamp, and a base64 signature over `timestamp + METHOD +` the full URL path excluding the query. RSA uses PSS/SHA-256; Ed25519 signs the message directly. Offline tests verify both signatures with ephemeral test keys; live credentials were not tested.
- **Creating an order:** [Create Order V2](https://docs.kalshi.com/api-reference/orders/create-order-v2) specifies `ticker`, `side` (`bid` = buy YES; `ask` = sell YES), string `count`, fixed-point dollar string `price`, `time_in_force` and `self_trade_prevention_type`. [The quick start](https://docs.kalshi.com/getting_started/quick_start_create_order) states HTTP 201 means accepted, not necessarily resting. The CLI deliberately limits quantities to positive safe whole numbers and prices to four decimal places; those are project constraints, not all possible exchange orders. No execution, fill, account cash, or ROI is claimed.
- **Cancellation routing:** [Cancel Order V2](https://docs.kalshi.com/api-reference/orders/cancel-order-v2) says an order ID alone cannot identify the exchange shard; `market_ticker` enables auto-routing when `exchange_index` is omitted. Without either, it defaults to shard 0. [Create Order V2](https://docs.kalshi.com/api-reference/orders/create-order-v2) routes an order by its ticker when its exchange index is omitted.
- **Account envelopes:** [Get Balance](https://docs.kalshi.com/api-reference/portfolio/get-balance) requires `balance`, `balance_dollars`, `portfolio_value` and `updated_ts`; [Get Positions](https://docs.kalshi.com/api-reference/portfolio/get-positions) requires `market_positions` and `event_positions` arrays; [Get Fills](https://docs.kalshi.com/api-reference/portfolio/get-fills) requires `fills` and `cursor`; [Get Settlements](https://docs.kalshi.com/api-reference/portfolio/get-settlements) requires a `settlements` array. These docs support the minimum envelope checks, not a claim that every nested field or response value has been independently verified.
- **Pagination:** The three list endpoints above describe pagination. This collector reads only the first page (fills and settlements request 200 rows; positions uses the endpoint default). The four sequential HTTP responses are not an atomic account snapshot and must not be treated as complete historical performance.
- **Public visibility:** This repository is public and the account workflow commits responses to the Pages source. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) publishes a static site from repository files. Key secrecy does not make published balances, positions or fills private. See the independently merged privacy warning in [`docs/DEMO_ACCOUNT.md`](../docs/DEMO_ACCOUNT.md) and [GitHub's sensitive-data removal guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

## Reproduced issues and corrections

1. **False connected state:** Before the change, a synthetic set of four HTTP-200 `{}` responses produced `connected: true` and a non-null `captured_at`. No exchange response was involved. The CLI now checks documented minimum response envelopes and types before declaring the capture connected. Valid zero balances and empty arrays remain valid. A failed request, transport exception or malformed response keeps `connected: false` and `captured_at: null`; transport exceptions are not echoed into output. The completion timestamp follows the sequential reads, rather than pretending the request start was their completion.
2. **Wrong cancellation shard:** Before the change, the dry-run printed `DELETE .../portfolio/events/orders/SYNTHETIC-ORDER` with no ticker or index. This can target the default shard 0 rather than the shard to which the order was auto-routed. The CLI now requires `--order-id` **and** `--ticker`, URL-encodes the values, and sends `market_ticker` while omitting `exchange_index`. Its existing dry-run default and demo-only boundary remain. This is verified with offline URL/signing-path tests, **not** a live cancellation. See [official V2 cancellation routing](https://docs.kalshi.com/api-reference/orders/cancel-order-v2).
3. **Source-free account rows:** The old connected-account renderer put a source link in a separate trailing row, not on each data row, and rendered list envelopes as large JSON values. The updated renderer expands the documented position, fill and settlement arrays and adds the exact corresponding demo endpoint to every rendered data row. It withholds all account values and says **unverified** if the capture time, required envelope or any exact allowed endpoint URL is missing or invalid. HTML in response strings is escaped. The source URL and schema check establish provenance/shape, not independent proof that a value is current or correct.
4. **Publication/refresh limitation:** A locally written failed capture is not guaranteed to replace a previously published file: `.github/workflows/demo-account.yml` stops before its commit step when the CLI exits nonzero; if credentials are absent, `account --ci` is a no-op. Existing snapshots therefore must be read as timestamped historical captures, never proof of a present connection. The connected display now states this explicitly. Workflow changes are outside this session's claimed scope and have been handed to integration. [GitHub step conditions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions) describe the default success condition.
