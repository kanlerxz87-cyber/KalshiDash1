## 3. Defects found and fixed in this session

### D-1 — the scrolling chat carried one event 99 times

*Measured:* the committed `data/live/feed.json` held **99 alerts, all from the single ticker
`KXPRESNOMD-28-AKLO`**, flapping between $0.80 and $0.00 between 16:28 and 19:26 UTC on 2026-11-20.
The two chat panes therefore showed one event repeated 99 times, and the high-ROI pane 18 copies of it.

*Cause:* `collapseDuplicates()` keyed on **(ticker, direction)** within a 3-minute window. An
up/down/up run every 120 seconds never matches, so the flood was structurally guaranteed.

*Fix (taken over from the stale PR #39):* one swing **per ticker per 15 minutes, direction-independent**;
the 3-minute window now applies only across detectors (candle vs trade vs sample describe the same
move); ties break oldest-first so a run collapses to its opening leg.

*Effect, measured:* 99 rows → **12**; high-ROI rows 18 → **1**. Published as **F-61**.

### D-2 — the "Resolved events" table could never fill

*Measured:* the live feed reported `untracked_settled_seen: 500` and `resolutions: 0`.

*Cause:* `applySample()` kept a resolution only when the ticker's row was still in `state.markets`,
but `state.markets` holds only markets sampled while they were **open**. A market leaves that set the
moment it settles, so every resolution was dropped as "untracked". `collectResolutions()` compounded
this by asking only for the series of currently-open markets, so a series whose markets had all
closed was never queried for its results.

This is a requirement gap, not a cosmetic one: the brief asks the dashboard to *"focus on tracking
live events until the events have resolved"* and to show *"how the event was resolved either yes or no"*.

*Fix:* the engine keeps a `followed` registry of every ticker it has ever seen; a resolution is kept
when the ticker is followed, not only when it is still open; `collectResolutions()` queries the series
of followed markets as well. Two selftest assertions cover the case that actually occurred.

*Verified:* `GET /markets?series_ticker=KXPGATOUR&status=settled&limit=5` (fetched this session)
returns four markets with `"result":"no"` and a `settlement_ts` — so the data the fix depends on is
there. Published as **F-63**.

### D-3 — the guard that was supposed to catch D-1 could not fail

*Measured:* the readability guard added by PR #39 was placed **after** the block that reports
violations and exits. Its `fail()` only pushed onto an array that was never read again, so the guard
could never fail a run. Running it against the 99-row flood it was written for **passed**.

*Fix:* the guard was moved ahead of the report and rewritten as a fixed-point check — the published
feed must be a fixed point of the engine's own `collapseDuplicates()`.

*Verified:* against the pre-fix feed the checker now prints
`✗ chat readability: 87 of 99 published alerts would be merged by the engine's own de-duplication rule
(worst ticker KXPRESNOMD-28-AKLO has 99 row(s))` and exits 1; against the corrected feed it exits 0.

A *"more than half of the alerts come from one ticker"* heuristic was tried first and **rejected**: after
the fix a genuinely active contract legitimately owns 12 of 12 rows over three hours, so that
heuristic flags correct feeds. Published as **F-62**.

## 4. The two workflows that failed on every scheduled run

*Measured from the GitHub API:*

| Workflow | Event | Runs | Outcome |
|---|---|---|---|
| `Refresh demo data snapshot` | schedule | 44860334644, 44824202497, 44802297690 | **failure** — step "Commit refreshed data" (capture, regenerate and link check all passed) |
| `live-alerts` | schedule | 44858392056, 44824102871, 44802297778 | **failure** — step "Commit the new sample" (selftest, sample and feed validation all passed) |
| `keepalive` | schedule | 2026-11-21T00:54:57Z | success |

*Why the log could not be read:* the job log is served from
`productionresultssa32.blob.core.windows.net`, which is unreachable from this environment
(`curl` returns HTTP 000); the only machine-readable evidence is the check-run annotation
**"Process completed with exit code 2."** `tools/external_link_audit.mjs` exists for the same reason.

*Root cause, established by measurement rather than by the log:*

1. The three writers used **three different `concurrency` groups** — `writer-${{ github.ref }}`,
   `live-alerts`, `refresh-data-${{ github.ref }}` — while `keepalive.yml`'s own header comment claimed
   "the other two writers queue behind this one instead of racing it (see the shared group name in
   live-alerts.yml and refresh-data.yml)". The comment was false; they raced.
2. They published **overlapping generated files**: `keepalive` staged `data/` (which contains
   `data/live/feed.json` and `data/live/state.json`) and `live-alerts` staged `data/live/` — the same
   two files — so `git rebase FETCH_HEAD` conflicted by construction; `refresh-data` staged `'*.html'`,
   which in git pathspec terms matches **all 90 HTML files** in the tree, including the hand-written
   `archive/` copy.
3. A failed rebase was fatal, and the old scripts could not report *which* command failed.

*Fix:* `scripts/publish-data.sh` publishes by **moving, never by merging** — fetch the remote tip,
`git reset --mixed FETCH_HEAD` (the working tree, i.e. the files just generated, is untouched), stage
**only** the given pathspecs, commit on top of that tip, fast-forward push; a rejected push re-fetches
and retries. Every failure path emits a `::error::` annotation, which is readable through the API
when the raw log host is not.

*Verification:* `tools/test_publish.sh` proves the properties against a scratch bare repository and
now runs in CI (`site-qa.yml`):

| Property | Test | Result |
|---|---|---|
| The published commit has exactly one parent (no merge) | test 1 | PASS |
| A publish with no changes does not move the branch | test 2 | PASS |
| A concurrent commit is neither reverted nor merged over | test 3 | PASS |
| Files outside the pathspec are never published | test 4 | PASS |
| A missing pathspec is rejected with a `::error::` annotation | test 5 | PASS |

**Status: not yet claimed fixed.** The repair is proved locally and by CI, but it is only *fixed* once
a scheduled run on `main` succeeds. That observation is recorded in `COORDINATION.md` and published as
**F-44** (with the parallel session's `fi` repair) and **F-60**; the earlier rows **F-45**, **F-46** and **F-57** were corrected to match.
