Questions, information needed, and answers

What must be settled before a decision here can be considered “reasonable”. Each item lists: what we already know (with source), what is missing, the suggested way to discover it, and the current best answer where one exists. Anything we could not confirm is on Flagged for Review rather than answered here.

Q-01 · Which demo account do we trade with?

  • Known. Demo accounts use mock funds; credentials are not shared with production; the recommended demo REST root is https://external-api.demo.kalshi.co/trade-api/v2 (Demo env docs). Authenticated calls need an API Key ID + private key created at demo.kalshi.co → Account & security → API Keys (Auth quick start).
  • Missing. No demo API key was supplied with this task, and none can be created without completing the demo signup flow — which requires a human and an email address.
  • How to discover it. Create a demo account at https://demo.kalshi.co/, generate an API key, then paste it into the browser-only form on the Portfolio page. Nothing is committed to the repo.
  • Answer for now. The site works without it (simulator + public data). Real demo order placement is available the moment a key is connected.

Q-02 · What exactly counts as an event's “dollar amount”?

  • Known. Market objects expose volume_fp, volume_24h_fp, open_interest_fp (contract counts) and price fields in dollars; notional_value_dollars means “the total value of a single contract at settlement”, not traded dollars (Get Markets). No event-level dollar total is documented.
  • Missing. A published definition of “highest dollar amount” for ranking purposes (yours, not Kalshi's).
  • How to discover it. Cross-check our estimate against GET /markets/trades sums for a few markets (count × price) and see whether the ordering changes; see SUG-03.
  • Answer for now. Ranking = volume_fp × last price, labeled “estimated”, with raw volume and open interest shown so you can re-rank yourself.

Q-03 · Which series belong to the five categories?

  • Known. GET /series returns category (primary) and categories[] (discovery list), and the category query filter matches exactly and case-sensitively (Get Series List). The set of valid category names is not enumerated in the docs.
  • Missing. The authoritative category name list, and whether Kalshi has categories that map cleanly to “gas prices”, “culture”, and “golf”.
  • How to discover it. Fetch GET /series once and collect distinct values of categories[]; the dashboard prints its matched series per category for audit on the dashboard and each category page.
  • Answer for now. Keyword discovery over live series, published per page so a reviewer can see exactly what was included and excluded.

Q-04 · Does the demo environment have live markets at all times?

  • Known. The demo environment is for testing with mock funds and “the price and behavior of markets in the demo environment may not be reflective of those in real markets” (Demo env docs). Exchange status is exposed at GET /exchange/status (Get Exchange Status).
  • Missing. A guaranteed minimum number of open markets in each of our five categories in demo — this varies and could be zero on some days.
  • How to discover it. Check the dashboard at several times of day; the category pages show per-category counts and the exchange-status endpoint.
  • Answer for now. Design assumes “possibly empty”: every table degrades to an explicit empty state instead of substituting data.

Q-05 · Can a static GitHub Pages site call the API directly (CORS)?

  • Known. Public market-data endpoints need no authentication (Market Data quick start). Whether the demo API sends permissive Access-Control-Allow-Origin headers is not documented anywhere we could verify.
  • Missing. A live browser test from the deployed origin.
  • How to discover it. Open the deployed site; if it reports “OFFLINE / API UNREACHABLE”, the console shows whether it is CORS or network. Fallback is a same-origin proxy (SUG-02).
  • Answer for now. UNVERIFIED — see Flagged F-01. The site never fabricates data if the call fails.

Q-06 · How do we keep price history without a backend?

  • Known. Official candlesticks exist at 1 / 60 / 1440-minute granularity, max 365 days back for 1-minute bars, and history beyond the cutoff moves to GET /historical/markets/{ticker}/candlesticks (Candlesticks, Historical Data).
  • Missing. Your retention requirement: do you need tick-level history, or are 1-minute bars enough?
  • How to discover it. Decide against the two options in SUG-01 / SUG-09; the difference only matters if you plan to evaluate sub-minute strategies.
  • Answer for now. 1-minute and up come from Kalshi; sub-minute comes from in-page samples, labeled as ours.

Q-07 · Which strategy definitions should the site support?

  • Known. The four templates on Strategies (favorite, longshot, momentum, mean reversion) are defined in code with explicit thresholds and run against real candlesticks; backtests ignore fees.
  • Missing. Your decision rules — e.g. do you want liquidity-based entries (spread, book depth), time-to-expiry filters, or event-driven entries (news, settlement date)?
  • How to discover it. Run the templates over a week of snapshot data (SUG-01) and look at which category/price-bucket produced errors; then pick rules to test.
  • Answer for now. None of the templates is validated as profitable; they exist to make the mechanics reviewable, not to recommend trades.

Q-08 · How should a “trade” be categorized?

  • Known. Fills/Orders carry outcome_side (yes/no) and book_side (bid/ask); bid ≡ yes and ask ≡ no, and action/side are deprecated with removal “not before May 28, 2026” (Order direction). V2 quoting is always from the YES leg: “bid means buy YES, ask means sell YES” (Create Order V2).
  • Missing. Whether you want buckets by entry price only (current) or by intent (momentum vs hedge vs expiry play), which is a labeling decision only you can make.
  • How to discover it. Trade a handful in the simulator, look at the auto-generated buckets on Portfolio, and tell us which axis matters.
  • Answer for now. Category × side × price bucket, with mode (simulator/demo) and timestamp.

Q-09 · How long must we track an event to catch resolution?

  • Known. Markets move from live endpoints to historical on a rolling cutoff published by GET /historical/cutoff (market_settled_ts) — Historical Data. Settlement timing after determination is governed by settlement_timer_seconds on the market (Get Markets).
  • Missing. The actual demo cutoff value — it changes over time and can only be read live.
  • How to discover it. Call GET /historical/cutoff from the browser and record it in the snapshot (SUG-01). Until then the events page polls live endpoints for the top rows.
  • Answer for now. Tracked while visible in the live endpoints; anything that ages out must be fetched from GET /historical/markets — not implemented in the browser build, and stated as such.

Q-10 · What are the rate limits we must design around?

  • Known. Requests cost tokens against a per-second budget; most requests cost 10 tokens; Basic/Advanced tiers can call GET /portfolio/balance once per second; 429 carries too_many_requests with no penalty and no Retry-After, so exponential backoff is the documented remedy (Rate Limits).
  • Missing. Your demo account's actual tier — readable from X-RateLimit-* headers, which a browser cannot expose to script unless the API sets Access-Control-Expose-Headers.
  • How to discover it. Read GET /account/endpoint_costs for non-default costs (documented on the same page) once authenticated; otherwise stay conservative.
  • Answer for now. The page polls at 5 s for one selected market and refreshes rankings on demand, which stays far below Basic-tier budgets; it stops and shows an error on 429 instead of hammering.
