SUG-01 · Persistent snapshot store (resolution history)

Problem. Today all tables are live-only. Kalshi moves settled markets to historical endpoints on a rolling cutoff (Historical Data), so a resolution seen this week can disappear from GET /markets later.

Options. (a) Commit a JSON snapshot to the repo from a scheduled workflow (no server needed; auditable via git history). (b) Run the Python collector in tools/ on a cron outside GitHub. (c) Keep live-only and accept data loss.

Trade-offs. (a) gives a free, transparent, versioned record but refreshes only as often as the workflow runs (GitHub Actions schedules are ~5 min at best and can be delayed). (b) is freshest but needs a machine you own. (c) costs nothing and loses the tracking requirement over time.

Recommendation. (a) hourly workflow writing data/snapshots/*.json, plus (b) if you want sub-minute history.

SUG-02 · Server-side WebSocket bridge

Problem. Kalshi's WebSocket API requires signed headers on the handshake, and browsers cannot set custom WebSocket headers — so this static site cannot stream (WS quick start, order direction docs for the use_yes_price note).

Options. (a) Keep 5-second REST polling (current). (b) Add a tiny WS→SSE relay (Cloudflare Worker / small Node service) that holds the signed connection and streams to the page. (c) Use min_updated_ts delta polling to cut request volume.

Trade-offs. (a) zero infrastructure, ~1–3 s latency floor, uses read budget. (b) true sub-second ticks and orderbook deltas, but adds a deployed service and a place for your demo key to live. (c) cheaper polling without any infra, still not a stream.

Recommendation. Do (c) now; add (b) only if second-level reaction actually changes your decisions.

SUG-03 · Better dollar-size ranking

Problem. There is no documented “dollar amount traded” field. notional_value_dollars is “the total value of a single contract at settlement” — i.e. $1 per contract, not volume (Get Markets). So the dashboard currently ranks by estimate: volume_fp × last price.

Options. (a) Keep the estimate label (current). (b) Rank by GET /markets/trades summing count × price per market — closest to a true traded-dollar figure, more requests. (c) Rank by series volume_fp with include_volume=true (documented field) for a coarser but official series-level view.

Trade-offs. (b) is the most defensible definition of “highest dollar amount”, but paginating trades for many markets costs read budget and time. (c) is cheap and official but not per-market or per-event.

Recommendation. (b) for a weekly “true notional” audit column, (a) for the live ranking.

SUG-04 · Explicit resolution pipeline

Problem. Resolution is read from Market.result (yes/no/scalar/"") plus settlement_ts / settlement_value_dollars. The docs also describe determination → settlement timing (settlement_timer_seconds) and that the response status enum (active, determined, finalized…) differs from the filter enum (open, settled…) — Get Markets.

Options. (a) Keep result-only display (current, safest). (b) Show the full lifecycle (status + determined vs finalized) so “awaiting settlement” is visible. (c) Add GET /events?with_nested_markets=true for event-level rollups (multi-market events like elections).

Trade-offs. (b) prevents misreading a determined-but-unsettled market as final. (c) is needed for events with several outcomes (e.g. “who wins the nomination” with many candidates).

Recommendation. (b) + (c), keeping result as the only source of YES/NO.

SUG-05 · Category filter fidelity

Problem. “Gas prices / elections / culture / crypto / golf” are matched by keyword rules over GET /series title, category, categories[] and ticker. Kalshi's own discovery categories are exact, case-sensitive strings on the category filter (Get Series List), and the real list of category names is not published in the docs we could read.

Options. (a) Keep keyword rules (current). (b) Enumerate the distinct categories[] values from a live series response once, then use Kalshi's exact category= filter. (c) Maintain an explicit allow-list of series tickers reviewed by you.

Trade-offs. (b) is the most “official” mapping and cheap to run, but depends on Kalshi's category names lining up with your five topics (e.g. golf may sit under a sports category). (c) is highest precision, needs human upkeep.

Recommendation. (b) with (a) as fallback, and publish the resulting mapping table on each category page for audit.

SUG-06 · Order lifecycle in the Trade page

Problem. The Trade page places a V2 limit order but does not list, amend or cancel resting orders. 201 only means accepted, and reads lag the engine briefly (Get Order).

Options. (a) Add a “My open demo orders” table with cancel (DELETE /portfolio/events/orders/{order_id}). (b) Add amend price/qty (POST …/amend). (c) Add queue position display (Get Order Queue Position) so you can see how far you are from a fill.

Trade-offs. (a) is needed to avoid leaving stray demo orders around; (c) is genuinely decision-relevant for fill probability but is a per-order call.

Recommendation. (a) now, (c) next, (b) only if you start using resting limit orders seriously.

SUG-07 · Fees in simulator accounting

Problem. The simulator books fills at price × quantity with no fee. Real Kalshi fees are per-contract and quadratic in price, with series-level fee_type / fee_multiplier (series fields); the schedule is published as a PDF on kalshi.com and rounding rules are documented in Fee Rounding.

Options. (a) Keep fee-free simulator, clearly labeled (current). (b) Apply the documented quadratic formula with the series' fee_type/fee_multiplier. (c) Show both gross and after-fee P&L columns.

Trade-offs. Cheap side orders (1–5¢) are where fees bite hardest; ignoring them overstates strategy quality. (c) preserves comparability with (a).

Recommendation. (c), with the formula and its source link printed next to the number.

SUG-08 · Durable decisions & multi-user review

Problem. Votes and the chosen path are browser-local, so two reviewers cannot see each other's choices and choices vanish when storage is cleared.

Options. (a) Keep browser-local (zero infra, current). (b) A “decision log” markdown file in the repo that a maintainer updates via PR — durable, reviewable, needs a commit. (c) Add a small backend (Issues/Notion/DB) for real multi-user state.

Trade-offs. (b) fits this repo's no-server design and the coordination workflow already in COORDINATION.md. (c) is the only true multi-user option.

Recommendation. (b) now: this page becomes the read-only view of DECISIONS.md.

SUG-09 · Chart fidelity (1-minute candles and live samples)

Problem. Candlesticks support only 1, 60 and 1440-minute periods (docs), so “seconds” resolution comes from our own 5-second polls (and 1-second sampling with a connected demo key), not from official history.

Options. (a) Keep two clearly-labeled sources (current). (b) Persist our samples to the snapshot store (SUG-01) so sub-minute history accumulates over time. (c) Add a “candles vs samples” toggle with source badges on every point.

Trade-offs. (b) is what actually makes a seconds axis meaningful on reload; (c) is nearly free and prevents misreading.

Recommendation. (c) immediately, (b) alongside SUG-01.

SUG-10 · Trust & verification UX

Problem. Verification is currently a page of tables. A reader cannot click a number in a live table to see its source field.

Options. (a) Add per-cell tooltips with endpoint + field name (e.g. “GET /markets → volume_fp”). (b) Add a “raw JSON” drawer for each row. (c) Timestamp every cell with fetch time and cache warning.

Trade-offs. (b) is the strongest audit tool and cheap for a static site; (a) is the biggest readability win for non-technical review.

Recommendation. (b) then (a); keep (c) as a footer line per table.
