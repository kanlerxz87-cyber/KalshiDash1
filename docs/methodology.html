Methodology

How every number on this site is produced, so a reviewer can reproduce or reject it. Source links for each factual claim: Sources & verification.

1 · Data source

Everything comes from Kalshi's demo Trade API, root https://external-api.demo.kalshi.co/trade-api/v2 (recommended demo REST root per the demo environment docs). Public market-data endpoints need no authentication (market data quick start). Requests are made by your browser when you open a page; the site stores no market data in the repository, so there is no stale snapshot to be mistaken for live data.

Freshness caveat, verbatim from the docs: market-data responses “are cached for a short time, so prices, sizes and status can lag the exchange by several seconds, and filtered listings can lag longer than a read of a single market” (source). That is why the selected market is re-read every 5 s and rankings refresh on demand.

2 · Category discovery (gas prices, elections, culture, crypto, golf)

  1. Read GET /series?include_volume=true (documented params: category, tags, include_product_metadata, include_volume, min_updated_ts — Get Series List).
  2. For each series row, lowercase the concatenation of title + category + categories[] + ticker.
  3. Assign the series to the first category whose keyword list appears in that text:
    CategoryKeyword rules (substring match)
    Gas pricesgasoline, gas price, gas prices, fuel price, fuel prices
    Electionselection, president, senate, house race, governor, mayor, ballot, congress
    Cultureoscar, grammy, emmy, box office, movie, film, celebrity, entertainment, culture
    Cryptocrypto, bitcoin, ethereum, btc, eth price, digital asset
    Golfgolf, pga, masters, ryder cup, open championship
  4. Series are then ordered by the official volume_fp field (contract volume across the series) so the busiest series are queried first.

Why not hard-code tickers? A hard-coded list would silently rot and would be unverifiable against “the five topics”. Keyword discovery is reproducible and every included series is printed on each category page for audit. Limitation: Kalshi's exact discovery-category names are not enumerated in the docs, so a series whose titles never mention the keywords can be missed — this is Flagged F-04.

3 · “Highest dollar amount” ranking

  • For each discovered series: GET /markets?series_ticker=…&status=open&limit=1000 (status filter values unopened|open|paused|closed|settled, max limit 1000, cursor pagination — Get Markets).
  • Estimated traded notional = volume_fp × last price, where last price is last_price_dollars (falling back to last_price cents ÷ 100, then to the YES bid/ask mid).
  • A second column uses volume_24h_fp × last price to show recent dollar flow instead of lifetime flow.
  • Raw volume_fp and open_interest_fp are always displayed, so the estimate can be re-derived or replaced.
  • Why an estimate at all: Kalshi documents notional_value_dollars as “the total value of a single contract at settlement in dollars” — a per-contract payout, not traded dollars — and no event-level dollar-volume field exists in the API reference. See Flagged F-05 and SUG-03.

4 · Prices, sizes and fixed-point strings

API quantities arrive as strings: FixedPointDollars (“responses emit up to 6” decimals) and FixedPointCount (2 decimals; minimum granularity 0.01 contracts) — Fixed-Point Representation. The client parses them with parseFloat, and prefers the *_dollars / *_fp fields, falling back to legacy cent fields only if the new ones are absent. Values that are absent stay blank (—).

5 · Chart (X = time, Y = price)

  • Windows of 1 h / 6 h / 24 h / 7 d use official candlesticks: GET /series/{series}/markets/{ticker}/candlesticks?start_ts&end_ts&period_interval where period_interval is one of 1, 60, 1440 minutes, timestamps in seconds, max 5,000 periods per request — Get Market Candlesticks. Plotted value = candle close (or price.close where the response is nested).
  • Windows of 60 s / 5 m / 15 m cannot be served by candlesticks (1 minute is the finest official interval), so the page samples GET /markets/{ticker} every 5 s while the tab is open, and marks those points as local samples. There is no sub-minute historical source in the public REST API; the WebSocket alternative requires an authenticated handshake (see Flagged F-07).
  • Y axis is the contract price in dollars ($0.00–$1.00 for binary markets).

6 · Liquidity / order book

GET /markets/{ticker}/orderbook returns orderbook_fp.yes_dollars and orderbook_fp.no_dollars as [price_dollars, count_fp] pairs sorted ascending by price, best bid last; only bids for both sides are returned because “a bid for yes at price X is equivalent to an ask for no at price (100−X)”, and order counts are not returned — Get Market Orderbook.

  • “How many contracts are available at a given price” = the count_fp of that level, aggregated at the price level (the docs state order counts are not returned, so this is contracts, not number of orders).
  • Cumulative column = running sum from the best price, i.e. how deep you can trade at that side.
  • Implied YES ask = 1 − best NO bid, and implied NO ask = 1 − best YES bid, using the equivalence above.
  • Level notional = level price × level contracts.
  • depth parameter: 1–100 levels per side, 0/omit for all; invalid values return 400 (same source). This page requests all levels and shows the 12 best per side.

7 · Resolution tracking

A market is considered resolved when its documented result field is yes or no (the enum is yes | no | scalar | ""), or when status is settled/finalized. settlement_ts and settlement_value_dollars (“only filled after determination”) are shown when present. If a market is settled but result is empty, the site prints “SETTLED — result field empty in API” instead of guessing a winner. Sources: Get Markets; note the docs list different status vocabularies for the filter and the response field, which is Flagged F-03.

Recent resolutions are read with GET /markets?status=settled&min_settled_ts=…. The docs warn “only one status filter may be supplied at a time” and that timestamp filters are “mutually exclusive from other timestamp filters and certain status filters”, so the client retries without the timestamp filter if the API answers 400 — Flagged F-06. Older settled data lives behind GET /historical/cutoff and GET /historical/markets (Historical Data), which the in-browser build does not query.

8 · Portfolio & trade accounting

  • Simulator: local ledger in localStorage. Buy fills book at the live demo price of the moment; cash and average cost are updated accordingly; nothing is sent to Kalshi. Starting cash $1,000 is a stated assumption of this tool, not a Kalshi figure (reset on the Portfolio page).
  • Demo account (optional): balance / positions / fills from GET /portfolio/balance, GET /portfolio/positions, GET /portfolio/fills; orders via POST /portfolio/events/orders (Create Order V2) with required fields ticker, side, count, price, time_in_force, self_trade_prevention_type and an optional client_order_id for deduplication — Create Order (V2). side is the YES-leg book side: “bid means buy YES, ask means sell YES” (same source), and a 201 means accepted, not resting — the page reports fill_count and remaining_count.
  • Legacy /portfolio/orders write endpoints return 410 Gone with code deprecated_v1_order_endpoint, which is why this site only uses the V2 path (same source). The legacy action/side fields are deprecated in favour of outcome_side/book_side (Order direction).
  • Signing: timestamp + METHOD + path, path signed from the API root without the query string, RSA-PSS/SHA-256 for RSA keys or Ed25519 for Ed25519 keys, base64 encoded, with the three KALSHI-ACCESS-* headers — Authenticated requests quick start. The key is never stored in the repository or sent anywhere except the demo API origin.

9 · Verification rule applied to this site

Every table row on Sources links to the official page it was read from, on 2026-11-20. Anything not confirmable from an official Kalshi source is left blank and listed on Flagged for Review — it is never inferred, estimated into a “verified” column, or silently defaulted. Values we computed ourselves (estimated notional, cumulative depth, implied asks) are labeled as our calculation next to the API fields they came from.

10 · Rate-limit discipline

Requests are deliberately few: one series scan + one markets call per matched series on refresh, one market read per 5 s for the selected ticker, and no balance polling loop (GET /portfolio/balance is limited to once per second on Basic/Advanced tiers, per Rate Limits and Tiers). On 429 the client surfaces the error and stops rather than retrying in a tight loop, matching the docs' “apply exponential backoff on 429”.
